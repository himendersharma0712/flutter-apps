The Simple Version (The "Walkie-Talkie" Analogy)

Imagine your app is a restaurant.

* The Parent (Quiz): This is the Head Chef in the kitchen. The chef is the only one who has access to the food supplies (the state of the app, like the current screen and the list of answers).
* The Child (ResultScreen): This is a Waiter. The waiter is completely "stateless"—they don't have ingredients, they don't have a stove, and they cannot cook anything.

The Head Chef wants the Waiter to let them know when a customer is ready for a new order. So, the Chef hands the Waiter a physical walkie-talkie (onRestart).

When the customer clicks the restart button, the Waiter doesn't cook the food themselves. They just press the button on the walkie-talkie and say, "Hey Chef, reset the table!" The Chef hears it back in the kitchen, clears the plates, and cooks a fresh meal (setState()).

The waiter never owned the power to change the restaurant; they just held the remote control that triggered the Chef to do it.

The Technical Version (The Architecture)

In modern declarative UI frameworks (like Flutter and Jetpack Compose), this architectural pattern is called State Hoisting combined with Unary Callbacks.

1. First-Class Functions and Closures

In Dart and Kotlin, functions are First-Class Citizens. This means functions are treated as objects; they can be assigned to variables and passed as arguments through constructors.

When _QuizState passes restartQuiz into the ResultScreen constructor, it isn't passing a copy of the code. It is passing a reference to a function object. Because of Lexical Closures, that function object permanently retains a reference to the exact memory scope where it was created (_QuizState).

2. State Hoisting

Instead of keeping the tracking variables inside the child widget, the data is "hoisted" (lifted up) to the closest common ancestor widget (Quiz). This ensures a Single Source of Truth. The child widget remains completely immutable and decoupled. It does not manipulate data; it only renders what is passed down to it via its constructor.

3. Unidirectional Data Flow

This architecture enforces a strict loop:

* Data flows down: The parent passes raw data configuration down to the stateless child.
* Events flow up: When a user interaction occurs, the stateless child executes the passed function reference (the callback). This triggers execution back in the parent's lexical scope, calling setState(), mutating the hoisted data, and marking the widget tree as "dirty" to schedule a complete framework redraw.
